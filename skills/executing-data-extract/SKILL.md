# Executing Data Extracts

Run ad-hoc dbt models, monitor the build, export results to cloud storage, and produce signed URLs for delivery.

## When to use

- dbt models have been generated under `dbt/models/ad_hoc/<ticket-id>/` (by the **fulfilling-data-requests-with-dbt** skill or manually).
- User wants to **build, export, and deliver** the extract.
- User wants to monitor or troubleshoot a running dbt build for ad-hoc models.

## Prerequisites

- dbt models exist under `dbt/models/ad_hoc/<ticket-id>/`.
- dbt profile configured for the target warehouse.
- Cloud storage credentials available (GCS service account key or workload identity for signed URLs).
- Use the **running-dbt-commands** skill for CLI usage. Prefer Makefile when available per project rules.

## Workflow

### 1. Validate before build

Confirm models exist and compile cleanly before materializing:

```bash
dbt compile --select path:models/ad_hoc/<ticket-id>/*
```

Review compiled SQL in `dbt/target/compiled/` for correctness — check tenant filter, date filter, and grain.

### 2. Build

```bash
dbt build --select path:models/ad_hoc/<ticket-id>/*
```

If the build fails:

| Failure type | Action |
|--------------|--------|
| SQL syntax error | Read compiled SQL, fix the model, rebuild |
| Permission / access denied | Check dbt profile and warehouse grants; escalate to platform team |
| Timeout | Consider partitioning or materializing incrementally |

### 3. Validate results

After a successful build, sanity-check the output:

```bash
dbt show --select <model_name> --limit 20
```

- Verify row count against expectations from the data request.
- Spot-check key fields: tenant, date range, IDs populated, no unexpected NULLs.
- If row count is 0, check tenant filter, date filter, and whether the source model covers the requested range.

### 4. Export to cloud storage

Use the appropriate strategy for your warehouse. See [references/export-strategies.md](references/export-strategies.md) for details.

**BigQuery → GCS (preferred):**

Use `scripts/export_to_gcs.py`:

```bash
uv run scripts/export_to_gcs.py \
  --project <gcp-project> \
  --dataset <schema> \
  --table <model_name> \
  --bucket <bucket> \
  --prefix exports/<ticket-id>/<model_name> \
  --format parquet
```

Or run the export SQL directly:

```sql
EXPORT DATA OPTIONS(
  uri = 'gs://<bucket>/exports/<ticket-id>/<model_name>/*.parquet',
  format = 'PARQUET',
  overwrite = true
) AS
SELECT * FROM `<project>.<schema>.<model_name>`;
```

### 5. Generate signed URLs

```bash
uv run scripts/generate_signed_url.py \
  --bucket <bucket> \
  --prefix exports/<ticket-id>/ \
  --expiry-hours 168
```

Default expiry: 7 days (168 hours). Adjust based on ticket requirements.

### 6. Deliver

Post signed URLs to the support ticket. Include:

- File count and total size.
- Format (Parquet, CSV, etc.).
- Expiry date of the signed URLs.
- Any caveats from the field coverage report (fields not modeled, approximations).

If the **jira-connector** MCP server is available, use `jira.post_comment(ticket_id, body)` to post directly.

## MCP tool integration (when available)

When MCP servers are configured, this skill delegates to them instead of running scripts directly:

| Action | MCP server | Tool |
|--------|-----------|------|
| Build models | `dbt-runner` | `dbt_build(selector)` |
| Check build status | `dbt-runner` | `dbt_run_status(invocation_id)` |
| Export to storage | `cloud-storage` | `export_bigquery_to_gcs(query, uri, format)` |
| Generate signed URL | `cloud-storage` | `generate_signed_url(bucket, path, expiry)` |
| Post to ticket | `jira-connector` | `post_comment(ticket_id, body)` |

## Output conventions

- Exported files: `gs://<bucket>/exports/<ticket-id>/<model_name>/*.parquet`
- Signed URLs: 7-day default expiry, one URL per exported file.
- Delivery message: Markdown table with columns: File, Size, URL, Expires.
